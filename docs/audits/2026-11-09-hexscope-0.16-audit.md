# Hexscope audit and proposed 0.16 scope

- **Date:** 2026-11-09
- **Released baseline:** `v0.15.0`, `a78caa337548383a154838383401e298bb174992`
- **In-progress work examined:** PR [#178](https://github.com/MykytaStel/hexscope/pull/178), head `4f92d9b36feca95c48cef69434586890488a713a`
- **Recommendation:** make 0.16 a release for actionable private batch reports and honest mobile copy confidence.

## Findings

1. **A batch in which every read fails cannot export diagnostics.** In the PR head, the entire coverage section, including diagnostics actions, is rendered only when `coverageByFormat.length > 0` (`apps/web/src/batch.ts:501,556-600`). Coverage rows are populated only for successfully completed items with a format and coverage (`batch.ts:112-120`). Thus an all-failed settled batch has a retry button but no diagnostic report, even though the diagnostic generator can represent `read_failed`. This is a source-level finding, not a reproduced browser test.
2. **Report row numbers are difficult to map back to files.** Diagnostics use the one-based position in the original batch (`apps/web/src/batch-diagnostics-report.ts:37-40`); batch rows display file names but no corresponding number (`batch.ts:459-470`). Filters and pagination make counting unreliable. The report deliberately excludes file names and paths, so a local way to match a number to its file would make the existing privacy boundary useful.
3. **Verification is bounded, and phone evidence is incomplete.** Web read-back is skipped for copies above 10 MiB (`apps/web/src/verification.ts:9-16`); the documented measurement came from a Playwright phone profile, not a physical phone. Unchecked copies must remain explicitly unchecked. The 0.14 audit records a successful iPhone clean-copy save/share flow, but that does not establish JSON/CSV report sharing, large-file memory behavior, Ultra HDR visual preservation, or Android behavior.
4. **The CSV slice is in review, not released.** PR #178 adds coverage and diagnostics CSV save/share, keeps the reports value-free, escapes spreadsheet formulas and uses `text/csv`. Its reported Web, E2E and CI checks passed at the examined head. Physical iPhone and Android behavior is still unverified. An empty coverage CSV would currently contain only a header and lose the total/not-read counts (`batch-coverage-report.ts:29-44`); this matters if the all-failed export path is enabled.
5. **New parser families lack a demonstrated priority.** Public issue listing was empty at audit time, which says nothing about private feedback or demand. Password-required PDF, constructed HEIF items and sequences, and other ZIP compression methods remain documented limitations. Adding one solely to fill a release would expand the safety and testing surface without evidence that it solves the most frequent user problem.

## Proposed 0.16.0 scope

The format-by-format display audit, including a larger photo inspector and PDF page navigator direction, is in [the format and interaction audit](2026-11-09-format-display-and-interaction-audit.md). This follow-up also records a corrected embedded-signature search risk, per-box photo controls, and the accurate PDF preview label.

### P0 — complete private reports and make them actionable

1. **Finish the existing CSV work in PR #178.** Save and share coverage and diagnostic reports in JSON and CSV, with the existing value-free fields and formula protection. Keep JSON version 1 compatible. Verify actual spreadsheet opening and mobile file handoff; avoid declaring a physical platform verified until tested.
2. **Export diagnostics for an all-failed batch.** Separate diagnostics availability from the existence of format coverage. Offer a meaningful coverage summary for zero successfully read files; for CSV include totals even when there are no format rows. Test one failed file, all failed, mixed failure/success and all-success batches, including both formats and retry behavior.
3. **Connect a diagnostic row to its file locally.** Show each file's stable, one-based original batch number in the list and enable direct navigation by number from an on-device diagnostic view. Keep the number stable under filters, pagination and retries; focus the chosen row and expose the number to screen readers. Reports remain name- and path-free. Document that these numbers identify positions in this batch only, not files across separate sessions.

### P1 — explain what happens to larger clean copies

4. **Show read-back eligibility before making a copy.** Clearly explain the 10 MiB threshold, the difference between generating a copy and verifying its findings, and what the person can do next. Keep a completed copy available when verification is skipped; never imply unchecked findings were removed. Cover single and batch flows, English and Ukrainian, keyboard and screen-reader announcements. Confirm the implementation checks the relevant output size and uses current verification states rather than duplicating the decision logic.
5. **Record a small physical-device matrix.** On an available iPhone: JSON/CSV save and share to Files, cancellation and retry, representative clean copies below and above the threshold, and Ultra HDR visual comparison where a suitable source exists. Record device, OS/browser, file and copy sizes, behavior and elapsed time; record memory only if it can actually be measured. Run equivalent checks on Android Chrome when hardware is available; mark unavailable cases open rather than replacing them with emulation. Do not raise the threshold without measurements and a bounded memory design.

### If capacity remains

- Examine private feedback in aggregate, if the maintainer makes it available, to select the next format or parser limitation. Require a representative, redistributable fixture and explicit read/clean/read-back and failure criteria before committing to a format. Do not collect file names or metadata values for prioritization.
- Extend the existing clean-copy corpus with incomplete and malformed cases for the formats touched by this release, with explicit negative assertions that unsupported or incomplete cases cannot become confirmed removals. Avoid interpreting fixture counts as overall accuracy.

## Release acceptance

- Mixed, all-failed and no-issue batches have coherent report actions; report counts agree across JSON and CSV, including zero readable files.
- Each diagnostic row can be located in the current batch without exposing a name or path in exported reports; filters, pagination, retry, keyboard and screen-reader behavior are covered.
- Both locales explain verification limits before copying and correctly report removed, still present and unchecked states. No skipped read-back is described as verified.
- CSV cells remain correctly quoted and safe against spreadsheet formula execution; report privacy tests verify that file names, paths, finding values and raw errors do not leak.
- Record automated checks and physical-device results separately. Device-dependent claims and Android coverage stay open if hardware or suitable files are unavailable.

## Audit limits

This audit inspected the released baseline, current roadmap and known limits, PR description and checks, and relevant batch/report/verification source. It did not rerun tests, conduct a security or full parser review, inspect private feedback, reproduce the all-failed scenario in a browser, or perform physical-device tests. CI status and the PR description are reported as existing evidence, not independent verification. The local checkout was on an older 0.14 branch; the revisions above were inspected directly without switching or changing the active branch.
