# Hexscope audit and proposed 0.16 scope

- **Date:** 2026-11-09
- **Released baseline:** `v0.15.0`, `a78caa337548383a154838383401e298bb174992`
- **In-progress work examined:** PR [#178](https://github.com/MykytaStel/hexscope/pull/178), head `4f92d9b36feca95c48cef69434586890488a713a`
- **Release scope:** private batch reports, honest copy confidence, richer file maps, and safer photo/PDF inspection.

## Findings

1. **A batch in which every read fails could not export diagnostics.** The PR head rendered reports only when at least one format was recognized, even though the diagnostic generator can represent `read_failed`. The 0.16 work now renders report actions for settled non-empty batches and includes zero-read totals in CSV. A browser test now forces two read failures, checks both exported diagnostic rows and follows one row back to its file.
2. **Report row numbers were difficult to map back to files.** The 0.16 work adds stable one-based numbers to batch rows and an on-device list linking diagnostic entries to their files. Exported reports continue to omit names and paths. Browser coverage now checks the navigation and keyboard activation of the format filter; pagination and physical screen-reader behavior remain open.
3. **Verification is bounded, and phone evidence is incomplete.** The single-file read-back gate checks the generated copy size (`apps/web/src/copyverification.ts:20-33`); the batch worker skips read-back when either the source or generated copy exceeds 10 MiB (`apps/web/src/worker.ts:343`). The documented measurement came from a Playwright phone profile, not a physical phone. Unchecked copies must remain explicitly unchecked. The 0.14 audit records a successful iPhone clean-copy save/share flow, but that does not establish JSON/CSV report sharing, large-file memory behavior, Ultra HDR visual preservation, or Android behavior.
4. **The CSV slice is in review, not released.** PR #178 adds coverage and diagnostics CSV save/share, keeps the reports value-free, escapes spreadsheet formulas and uses `text/csv`. The 0.16 work adds a total row to CSV even when no format was recognized. Physical iPhone and Android behavior is still unverified.
5. **New parser families lack a demonstrated priority.** Public issue listing was empty at audit time, which says nothing about private feedback or demand. Password-required PDF, constructed HEIF items and sequence decoding, and other ZIP compression methods remain documented limitations. 0.16 adds structural HEIF relationships and timing, not a decoder. Its comparison view remains a two-file comparison and does not measure or certify a sharing service.
6. **The batch copy-size notice omitted one limit.** The batch worker skips read-back when either `bytes.length` or `c.bytes.length` exceeds 10 MiB (`apps/web/src/worker.ts:343`), while the single-file gate checks only the generated Blob (`apps/web/src/copyverification.ts:20-33`). The single-file notice names clean-copy size; the batch notice names both source and clean-copy size. Both keep affected findings **Not checked**.

## Proposed 0.16.0 scope

### P0 — complete private reports and make them actionable

1. **Finish the existing CSV work in PR #178.** Save and share coverage and diagnostic reports in JSON and CSV, with the existing value-free fields and formula protection. Keep JSON version 1 compatible. Verify actual spreadsheet opening and mobile file handoff; avoid declaring a physical platform verified until tested.
2. **Export diagnostics for an all-failed batch.** Separate diagnostics availability from the existence of format coverage. Offer a meaningful coverage summary for zero successfully read files; for CSV include totals even when there are no format rows. Test one failed file, all failed, mixed failure/success and all-success batches, including both formats and retry behavior.
3. **Connect a diagnostic row to its file locally.** Show each file's stable, one-based original batch number in the list and enable direct navigation by number from an on-device diagnostic view. Keep the number stable under filters, pagination and retries; focus the chosen row and expose the number to screen readers. Reports remain name- and path-free. Document that these numbers identify positions in this batch only, not files across separate sessions.

### P1 — explain what happens to larger clean copies

4. **Show read-back eligibility before making a copy.** Explain the separate 10 MiB gates: single-file verification checks the generated copy; batch verification checks both the source and generated copy. Explain the difference between making a copy and verifying its findings, and what the person can do next. Keep a completed copy available when verification is skipped; never imply unchecked findings were removed. Cover single and batch flows, English and Ukrainian, keyboard and screen-reader announcements. Confirm the implementation follows the existing size gates rather than duplicating them.
5. **Record a small physical-device matrix.** On an available iPhone: JSON/CSV save and share to Files, cancellation and retry, representative clean copies below and above the threshold, and Ultra HDR visual comparison where a suitable source exists. Record device, OS/browser, file and copy sizes, behavior and elapsed time; record memory only if it can actually be measured. Run equivalent checks on Android Chrome when hardware is available; mark unavailable cases open rather than replacing them with emulation. Do not raise the threshold without measurements and a bounded memory design.

### Deferred beyond 0.16 — repeatable sharing-path study

The existing comparison inspects one selected pair and now supports a bounded
image wipe. It does not group multiple pairs by channel and mode, record test
conditions, or aggregate samples. A future lab needs explicit pairing for
renamed/duplicate files, complete/partial/unchecked outcomes, value-free
exports, and copy-specific results. It must never generalize a small sample
into a guarantee about an app. This is a separate follow-up, not a 0.16
release claim.

### If capacity remains

- Examine private feedback in aggregate, if the maintainer makes it available, to select the next format or parser limitation. Require a representative, redistributable fixture and explicit read/clean/read-back and failure criteria before committing to a format. Do not collect file names or metadata values for prioritization.
- Extend the existing clean-copy corpus with incomplete and malformed cases for the formats touched by this release, with explicit negative assertions that unsupported or incomplete cases cannot become confirmed removals. Avoid interpreting fixture counts as overall accuracy.

## Release acceptance

- Mixed, all-failed and no-issue batches have coherent report actions; report counts agree across JSON and CSV, including zero readable files.
- Each diagnostic row can be located in the current batch without exposing a name or path in exported reports; filters, pagination, retry, keyboard and screen-reader behavior are covered.
- Both locales explain verification limits before copying and correctly report removed, still present and unchecked states. No skipped read-back is described as verified.
- CSV cells remain correctly quoted and safe against spreadsheet formula execution; report privacy tests verify that file names, paths, finding values and raw errors do not leak.
- Two-file comparisons remain bounded to the selected files and do not claim how a messaging or sharing service behaves in general.
- Record automated checks and physical-device results separately. Device-dependent claims and Android coverage stay open if hardware or suitable files are unavailable.

## Audit limits

This follow-up inspected the current 0.16 worktree and reran `pnpm --filter web test` (50 files, 468 tests passed), `pnpm --filter web build` (passed), `cargo test --all` (passed), and the targeted Playwright batch suite (25 passed, 3 phone-share tests skipped in the desktop project). The suite exercised the phone profile in an emulator; it does not count as a physical-device result. Physical iPhone/Android behavior, pagination edge cases and screen-reader use of the new controls remain open. The audit was not a full security or parser review, and private feedback was unavailable.
