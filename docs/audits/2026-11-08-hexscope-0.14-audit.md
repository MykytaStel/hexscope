# Hexscope audit and proposed 0.14 scope

- **Date:** 2026-11-08
- **Audited revision:** `main` at `9760171` (after the `v0.13.0` release)
- **Recommendation:** make 0.14 a confidence and mobile-reliability release, with one visible Web feature: batch coverage by format.

## Executive summary

Hexscope has a strong safety foundation for a file parser: Rust core forbids
unsafe code, the browser's CSP permits only same-origin code and requests, the
CI exercises parser fuzz targets, and the code has a value-free clean-copy
verification contract shared with the Web and CLI. The latest release's full
CI, fuzz, browser, cross-platform build and live-site checks passed.

No dependency advisory was reported by `cargo audit` or the full `pnpm audit`
on 2026-11-08. Neither advisory command currently runs in CI, so this is a
snapshot rather than a guard against future vulnerable updates.

The biggest product gap is confidence at the edges: `hexscope coverage` now
describes the files a person supplied, but it does not yet measure parser and
cleaner quality against a per-format expectation corpus. The Web also skips
read-back verification for clean copies larger than 10 MiB, and real iOS and
Android behavior remains unverified. These should shape 0.14 before adding
more uncommon formats.

## Audit scope and evidence

- Read the product direction, known limitations, clean-copy coverage contract,
  release process, security notes, Cargo and pnpm manifests, CI workflows,
  parser/core/CLI/WASM structure, Web worker/batch/feedback paths, and test
  inventory.
- Ran RepoPilot 0.25 in full/default and strict modes. It discovered 921 files,
  analyzed 437 source/document files and skipped 43 binary files. The default
  profile reports four stable signals: one dependency-cycle candidate and
  three high fan-out modules. Strict mode reports 792 items, 788 of which are
  hidden by default; most are preview, experimental, or maintainability
  heuristics. Treat those as leads, not 792 confirmed defects.
- Confirmed the reported Web cycle in source. `batch.ts` refers to
  `PhotoSignal` as a type, while `photo-mosaic.ts` imports the runtime
  `cleanable` function. The cycle exists in the source/type graph; the
  `PhotoSignal` edge is erased and does not establish a JavaScript runtime
  import cycle.
- Ran `cargo audit` against `Cargo.lock`, full `pnpm audit`, and
  `cargo tree --duplicates --locked --offline`. The two advisory scans found
  zero known vulnerabilities. Duplicate versions exist for some transitive
  compression, proc-macro and test dependencies; no user-facing issue was
  established from those duplicates.
- GitHub open-issue search returned no open issues. This does not include
  private feedback stored by the site, and the site's aggregate counters do
  not record file formats.
- Did not rerun the test suite for this read-only audit. The latest release
  CI already passed `cargo test --all`, clippy, formatting, large-file tests,
  WASM/MSRV checks, fuzzing, browser E2E, cross-browser and the live-site check.
- The repository contains roughly 689 Rust `#[test]` declarations, 46 Web
  unit-test files and 24 browser E2E files. Counts indicate a substantial test
  base, not per-format coverage or physical-device evidence.

## Findings

### P1 — coverage describes inputs, not parser or cleaner quality

`hexscope coverage` aggregates complete, partial and unsupported reads for
the local files it receives. It does not yet compare expected findings,
clean-copy results, false positives, parser completeness or measured
performance for every supported format. The roadmap's previous scorecard
proposal explicitly included those regression expectations, but the shipped
0.13 scope covers the aggregate API and CLI report only.

**Impact:** the report is useful for inspecting a batch, but it cannot yet
support a repository-wide claim that every advertised format or clean-copy
capability has been exercised against known-good and known-bad examples.

**0.14 action:** add a deterministic corpus from synthetic and redistributable
fixtures. For each format, record expected findings and incomplete cases; for
every `Removed` capability, run a source-to-clean-copy read-back assertion.
Publish a value-free CI summary with per-format coverage and regression
outcomes. Keep accuracy as measured cases, never one unqualified percentage.

**Evidence:** `docs/roadmap.md`'s 0.13 scorecard follow-up;
`docs/verification-coverage.md`; `crates/hexscope-core/src/verification.rs`;
`crates/hexscope-core/src/coverage.rs`.

### P1 — large Web clean copies are deliberately unverified

The Web skips read-back verification for copies larger than 10 MiB. The
browser can open larger files (up to the documented 2 GiB input limit), and
non-video inputs plus their clean copy can be held in memory together. The
current UI preserves the conservative **Not checked** meaning; it does not
claim that an unchecked removal succeeded.

**Impact:** people can receive a useful copy without the strongest assurance
the product offers for smaller files, and the gap is most visible on phones.

**0.14 action:** record memory, time and result behavior on physical iOS Safari
and Android Chrome for representative photos, PDFs and archives. Set explicit
per-device verified-copy limits and explain them before saving. Increase the
10 MiB threshold only if measurements support it; otherwise keep the honest
unchecked state and improve the user's choice and recovery path. Do not promise
streaming until the Rust/WASM parser has a bounded incremental design.

**Evidence:** `docs/verification-coverage.md:104-115`;
`docs/known-issues.md:154-160`.

### P1 — physical-device release criteria remain open

The 1.0 checklist requires iOS Safari and Android Chrome, while the known
issues document explicitly says the Ultra HDR copy has only fixture-based
read-back and has not been opened and visually compared on a physical iPhone.
Playwright E2E and browser-engine checks do not prove device memory, file
picker, share-sheet or screen-reader behavior.

**0.14 action:** use a short repeatable device matrix covering file pick,
analysis, clean copy, read-back status, share/download, backgrounding and a
large input on both platforms. Record device/OS/browser, file size, elapsed
time, observed peak memory where available, and result. Keep unresolved rows
visible; do not replace them with emulated runs.

**Evidence:** the 1.0 stability checklist in `docs/roadmap.md`;
`docs/known-issues.md:56-63` and `docs/known-issues.md:132-137`.

### P1 — the optional feedback attachment starts selected

When the user opens “Report a problem with this file”, the structure-report
checkbox is initialized as checked (`feedback.ts`). The UI gives a preview and
describes what is attached, but the server comments and guide say the person
must tick the checkbox. A structure report omits file content and finding
values, yet it can still disclose the file's format and layout; opt-in should
match the text.

The page clearly lists the form fields sent on explicit submission. Separately,
the roadmap's “no telemetry” phrase coexists with aggregate page/device/
language/referrer counts. The feedback handler stores message, optional
contact, page, locale, version, device and optional structure report; it does
not have an IP column. The repository cannot establish what infrastructure
logs at the network edge.

**0.14 action:** default the structure-report box to unchecked; preserve the
full preview; say exactly what is submitted and stored, including aggregate
visit counts and the distinction between application storage and hosting
infrastructure. Keep file bytes out of all requests.

**Evidence:** `apps/web/src/feedback.ts:107-121, 152-166`;
`apps/web/server/feedback.ts:1-5, 18-27, 54-66`;
`apps/web/src/count.ts:20-36`; `docs/roadmap.md` principles.

### P2 — dependency advisory scans are absent from CI

The current Cargo and pnpm lockfiles have zero known advisories in today's
scan, and Dependabot proposes monthly updates. CI does not run an advisory
check when dependencies change.

**0.14 action:** add locked Rust and JavaScript advisory checks to CI and a
scheduled run. Document any accepted exception with a reason and revisit date.

**Evidence:** `.github/workflows/ci.yml`; `.github/dependabot.yml`; clean
`cargo audit` and `pnpm audit` results from 2026-11-08.

### P2 — pull requests receive duplicate full CI runs

CI runs on every branch push and on `pull_request`. The 0.13 code PR and the
roadmap follow-up each produced two full CI runs for the same head commit,
including fuzz and browser shards.

**Impact:** extra runner use and slower feedback, with no independent signal
from the identical second run.

**0.14 action:** simplify the event policy or use a reviewed concurrency
strategy that leaves one green required check per PR head and retains checks
for direct branch work. Verify branch protection before changing triggers.

**Evidence:** `.github/workflows/ci.yml:5-8`; CI runs for PRs #173 and #174.

### P2 — source graph cycle and high-change modules

The batch/photo-mosaic cycle is type-only on one edge, not a runtime cycle.
The static graph also shows composition hubs in `analyzer.ts`, `drawer.ts` and
`hexscope-core/src/lib.rs`. Several high-change implementations are large:
`clean.rs` (2,615 lines), CLI `main.rs` (1,455), PDF page parsing (1,760),
and Office ZIP parsing (1,467).

**0.14 action:** move shared batch types behind a small model module to remove
the type cycle. Deepen the cleaning/CLI modules only when the corpus or
verification work touches a clear seam. Do not split files solely to meet a
line-count threshold; the 40-module `lib.rs` is intentionally an export and
module index.

**Evidence:** RepoPilot default-profile signals, verified against
`apps/web/src/batch.ts:32` and `apps/web/src/photo-mosaic.ts:1`;
`crates/hexscope-core/src/lib.rs` and the cited module sizes.

### P2 — security release wording disagrees with release mechanics

`SECURITY.md` says “the site is the only release.” The release guide and
workflow publish the site, CLI archives, crates and Homebrew formula from one
version. This can confuse which artifacts need a security fix when the Rust
core is affected.

**0.14 action:** clarify that urgent site fixes can ship immediately, and that
core fixes also require new crate/CLI artifacts and an updated Homebrew
formula.

**Evidence:** `SECURITY.md:25`; `docs/releasing.md:3-6, 40-82`.

## Proposed 0.14 scope

**Theme:** confidence for whole batches and clean copies on the devices people
use to share them.

### Commit to 0.14

1. **Browser batch coverage** — reuse the core complete/partial/unsupported
   statuses to summarize a local batch by format and let people focus on the
   files that need attention. Keep the report value-free and on-device.
2. **Fixture-backed confidence gates** — cover parser expectations and every
   advertised clean-copy removal capability with deterministic fixtures and
   source-to-copy read-back. Emit a value-free per-format CI summary.
3. **Mobile copy confidence** — record the iOS Safari and Android Chrome
   matrix, set honest per-device limits, and show **Not checked** wherever the
   output was not read back. Do not raise browser memory use to manufacture a
   green result.
4. **Feedback privacy clarity** — make structure-report attachment opt-in by
   default and align the UI, server data schema, security note and roadmap's
   local-analysis statement.
5. **Dependency gates** — run Cargo and pnpm advisory checks in CI and on a
   schedule, with explicit handling of accepted advisories.

### Include if capacity allows

- Remove duplicate full CI runs while preserving branch feedback.
- Break the type-only batch/photo-mosaic cycle and extract a focused seam from
  `clean.rs` or CLI `main.rs` only where the new confidence work benefits.
- Update `SECURITY.md` release wording alongside the privacy copy.

### Defer

Do not add several rare parser families in 0.14. Known gaps include
password-protected PDFs, ZIP compression methods other than stored/deflate,
constructed HEIF items and sequences, `.svgz`, and less common JPEG modes.
There are no open public issue requests to rank these. Revisit them against
private feedback and explicit user demand after the confidence gates exist.

## Readiness and limitations

- The advisory scans were clean on the audit date; they do not guarantee future
  dependency safety.
- Static analysis is not runtime proof. Its strict profile reports many
  experimental and preview suggestions; the production source/type cycle was
  manually checked as type-only.
- No parser tests were rerun as part of this audit. Release CI had already
  passed on `v0.13.0` before the roadmap-only follow-up.
- The four-week “no false alarm left unfixed” 1.0 criterion cannot be verified
  from public issues alone because private feedback is stored separately.

## 0.14 candidate follow-up

The candidate branch adds a value-free CI scorecard for all 14 clean-copy
formats. Complete files are cleaned and parsed again; every covered finding
present in a fixture must be reported removed. Generated MP3, FLAC and Ogg
streams exercise the readable tag families, Office fixtures cover the full
ZIP property set and an embedded photo without GPS, and a focused CFB property
test covers the less common Office 97 fields. The MP3 contract was narrowed:
`TXXX` remains uninspected, so `organization` and `location` are not claimed
as verified ID3 findings.

The user reports the iPhone clean-copy save/share flow now works. The
`v0.14.0` release shipped on 2026-11-08 with all five platform archives and
checksums, four crates published, and the Homebrew formula upgraded and
tested. Android hardware is unavailable for this release cycle, so Android
Chrome and the rest of the physical-device matrix remain open. The 10 MiB Web
read-back limit also remains unchanged pending real-device memory and timing
measurements.
