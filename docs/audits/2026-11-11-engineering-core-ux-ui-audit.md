# Hexscope: інженерний, core, кодовий та UX/UI аудит

Дата: 2026-11-11. Це аудит і пропозиції розвитку, без змін продуктового коду.

## Межі та базова версія

- Виконуваний checkout: `feat/0-14-audit-plan`, commit `3b5ccc9`, workspace version 0.14.0, із наявними незакоміченими змінами UI/PDF/embedded search. Вони збережені.
- Свіжіший код перевірено читанням локального remote-tracking `origin/main` на `e2c6409`, а також гілки `feat/0-18-accumulation` на `30aafe5`. Остання є предком цього `origin/main`, а не новішою базою. Fetch, live production та GitHub CI у цьому проході не перевірялися.
- Висновки про runtime стосуються лише поточного checkout. Висновки про новіший код — статична перевірка. Це не runtime-сертифікація 0.17/0.18.
- Не використовую умовні оцінки «8/10»: без визначеної методики вони приховували б різну силу доказів.

## Головний висновок

Найсильніша сторона Hexscope — пояснюваний локальний аналіз: знахідка пов'язана зі структурою й байтами, а очищена копія має окремий консервативний результат перевірки. Подальше розширення форматів має сенс, але найбільший інженерний виграш зараз дадуть контроль ресурсів, сильніші семантичні перевірки writers і простіший шлях від висновку до підтвердженої копії.

Спільне Rust-ядро, заборона unsafe, окремі parser families, каталог finding/reason codes, property tests, fuzz smoke, перевірка пакувань/розмірів у CI — корисна основа. Framework rewrite сам по собі не виправить перелічені нижче ризики.

## Знахідки та ризики

### 1. P1 — звичайні файли читаються цілком, без спільного admission budget

**Підтверджено в коді**, також у `origin/main`: `apps/web/src/worker.ts:242–255` читає non-movie файл через `File.arrayBuffer()`, далі викликає синхронний WASM parser. У CLI `main.rs` є `fs::read` у check/clean/readback; спеціальний large-movie шлях не робить усі формати потоковими.

**Ризик:** велике зображення, PDF або ZIP може потребувати значно більше пам'яті, ніж його розмір на диску: source buffers, дерево, декодовані дані, output і readback. OOM не відтворювався; це підтверджена архітектурна експозиція, не доведений crash.

**Додати:** профілі ресурсів для preview/inspect/clean/verify, ранню перевірку розміру, сумарний бюджет decoded bytes і nodes, явний частковий результат при досягненні межі. Зберегти наявні локальні ліміти форматів: ZIP entries, PDF decoding, MIME depth уже обмежуються.

**Готово коли:** для великого non-movie fixture застосунок відмовляється або переходить у bounded inspection до повного allocation; виміряні peak RSS і час, повторний файл відкривається без перезавантаження вкладки.

### 2. P1 — скасування RPC не може перервати синхронний WASM parse

**Підтверджено:** `rpc.ts:125–132` надсилає cancel і завершує promise; WASM виклик у `worker.ts:249` синхронний. Повідомлення cancel обробляється, коли worker повернеться до event loop. Timeout із `terminate()` існує, але parse виклики в `analyzer.ts` передають `undefined` замість deadline. У large-movie parse UI чесно позначає синхронну стадію як non-cancellable.

**Ризик:** важкий parse може затримати наступні запити worker навіть після відмови від попередньої операції. Це не твердження, що кожна кнопка Cancel у UI працює неправильно.

**Додати:** deadline для важких операцій, можливість аварійного перезапуску читача, session/generation token для всіх stateful replies; довгостроково — окремий disposable worker для parse/verify або кооперативні parser checkpoints.

**Готово коли:** навмисно повільна операція припиняється, наступний файл відкривається, старі replies не змінюють поточний стан. Втрата worker-owned даних має бути явно показана.

### 3. P1 — fuzz roundtrip перевіряє виконання, але слабко перевіряє правильність

**Підтверджено**, також у `origin/main`: `crates/hexscope-core/fuzz/fuzz_targets/clean_roundtrip.rs:18–21` ігнорує результат повторного clean та результат `verification::compare`. Assertions перевіряють однаковий формат і непорожнє дерево.

**Наслідок:** target не зловить усі випадки, коли writer повернув копію з неправильно збереженими або неправильно вилученими даними. Окремі fixture/property tests уже перевіряють payload/pixels; проблема саме у силі універсального fuzz oracle.

**Додати:** format-specific invariants: збереження media payload там, де обіцяно, відсутність нових findings, відсутність суперечностей між removed і output, повторна читабельність. Ідемпотентність bytes вимагати лише для форматів, де вона є контрактом; неповні або навмисно retained дані не повинні створювати хибних падінь.

### 4. P1 — розширення writers потребує незалежного читача

**Інженерний ризик:** clean і readback через спільний parser можуть мати однакову сліпу зону. Наявні порівняння та fixtures корисні; успішний self-readback не доводить універсальну сумісність чи повноту виявлення метаданих.

**Додати:** розширювати незалежні перевірки на кожну нову capability: інший metadata reader, звичайний переглядач документа, payload/pixel comparison; мінімізований redistributable corpus. Фіксувати не тільки false positives, але й відомі пропуски та відмови writer.

### 5. P1 — перевірка копій понад 10 MiB лишається продуктовою прогалиною

**Підтверджено**, також у `origin/main`: `apps/web/src/verification.ts:9–16` задає `MAX_VERIFY_BYTES = 10 MiB`. Коментар містить історичне emulation-вимірювання, а не результат цього аудиту. Це чесний guardrail, не дефект класифікації.

**Додати:** перед створенням копії показати, чи доступна readback-перевірка для цього розміру; після — три окремі стани «створено / перевірено / не перевірено». Дати локальну CLI-інструкцію для важких копій. Збільшувати cap лише після вимірювань на реальних пристроях та зміни memory model.

### 6. P2 — `complete: bool` має неоднозначну семантику для API-користувача

**Підтверджено:** у `summary.rs` невідомий формат може мати `complete = true`, бо його fallback byte tree не містить помилок. `CoverageStatus::from_summary` правильно повертає `unsupported`; це не знайдена помилка поточного coverage UI.

**Ризик:** новий consumer може випадково використати bool як «формат повністю перевірено».

**Додати:** рекомендувати typed inspection status як основний API; розділити structural accounting, metadata coverage і verification outcome. Не ламати наявний JSON без версії/міграції.

### 7. P2 — центральні модулі концентрують забагато відповідальностей

На `origin/main`: `clean.rs` — 2740 рядків, `analyzer.ts` — 1308, `drawer.ts` — 1349, `visual-direction.css` — 2232. Кількість рядків — індикатор навігаційної вартості, не доказ низької якості.

**Додати:** виділяти глибокі модулі за поведінкою: format writers; file session; inspection view; copy workflow; evidence navigation. Зовнішній інтерфейс має бути меншим за внутрішню реалізацію. Не дробити на десятки одноразових helpers і не переписувати все одразу.

**Готово коли:** зміна одного writer не потребує редагування інших форматів; lifecycle ресурсу має одного власника; existing contract tests проходять без дублювання логіки у Web.

### 8. P2 — Firefox/WebKit покривають лише вузький smoke path

**Підтверджено**, також у `origin/main`: `apps/web/playwright.config.ts:31–39` запускає для них тільки `cross-browser.e2e.ts`. Там два photo-сценарії: читання та keyboard clean-copy. Більша матриця працює в Chromium.

**Додати:** невеликий critical suite для PDF redaction, ZIP navigation, download, worker reset, batch, offline/share target; mobile WebKit profile. Реальний iPhone share sheet, Android handoff і screen reader лишаються окремими ручними gates.

### 9. P2 — довідник архітектури відстає від реалізації

**Підтверджено**, також у `origin/main`: `CONTRIBUTING.md:92–97` каже про два WASM builds; `parser-builds.ts` містить media/pdf/docs/audio, окремо є raster. Опис маршрутизації нових форматів теж потребує синхронізації з feature flags.

**Додати:** коротку актуальну карту залежностей, таблицю features/build families та бюджетів із посиланнями на CI; перевіряти доступність кожного advertised формату в CLI і відповідній WASM family.

### 10. P2 — огляд змішує висновок, дію і довідкові метадані

**Runtime-спостереження поточного checkout:** desktop photo має виразну CTA, читабельне прев'ю й локальну карту. На 390 px PDF після висновку й CTA переходить у довгий список властивостей; preview документа не видно на першому екрані. Це UX-гіпотеза для покращення, а не функціональна поломка.

**Спробувати:** короткий огляд із трьох частин — що знайдено, що не перевірено, що зробить копія. Метадані відкривати за категорією, дія/результат залишаються поруч. У новішому `origin/main` уже є photo inspector, evidence overview і collapse metadata: повторно оцінити їх runtime перед редизайном, а не реалізувати вдруге.

### 11. P3 — українське формулювання PDF revision втратило кількість

**Відтворено:** `report.pdf` показує «Відредаговано: раз після першого збереження…». `i18n-uk.ts:1582` перекладає `once` як `раз`; у `origin/main` та сама фраза є на рядку 1779.

**Виправлення:** «один раз після першого збереження…». Для динамічних значень поступово переходити від regex над англійським реченням до message ID + параметрів + українських plural rules.

## UX/UI напрям

Зберегти нинішні сильні сторони: стриману палітру, один помітний primary action, можливість перейти до байтів, локальну карту, однакову мову доказів. У перевірених viewport не було горизонтального overflow; це не перевірка всіх режимів, контрастів і діалогів.

Пропозиції для перевірки з користувачем:

1. **Одна відповідь на перший погляд:** «Є геолокація і серійний номер; 2 частини не перевірено». Загальна кількість фактів лишається другорядною: дата чи назва програми не мають виглядати рівнозначними координатам.
2. **Preview + evidence:** вибір знахідки одночасно підсвічує область/вузол, пояснює походження й доступну дію. Для PDF явно розрізняти реконструйоване preview та повний renderer.
3. **Копія як завершений сценарій:** джерело → заплановані зміни → створений файл → фактична перевірка → відкрити/зберегти/поділитися. Існуючі частини потоку об'єднати, а не створювати ще один cleaner.
4. **Менше технічних режимів у першому виборі:** основний сценарій перевірки; інспектор структури й навчальні інструменти за явним переходом. Технічні можливості зберегти.
5. **Mobile:** status і CTA видно без довгого скролу; керування областями працює пальцем, клавіатурою та без точного drag. Перевірити 200% zoom і VoiceOver на фізичному пристрої.

## Нові фічі та експерименти

Це пропозиції, не обіцянка реалізації; частина розвиває наявні compare, receipts, coverage і mosaic.

| Ідея | Навіщо | Обмежений перший зріз | Доказ готовності |
|---|---|---|---|
| **План змін перед копією** | Розуміти наслідки до збереження | Read-only список removed/kept/unchecked для одного формату, на основі core capabilities | План не обіцяє більше, ніж writer і readback |
| **Пояснюване порівняння** | Відповісти «що змінилося» мовою людини | Над наявним byte/tree diff показати зміни finding kinds і payload status | Відомі content/metadata зміни розділяються без хибного «зображення однакове» |
| **Один профіль перевірки для Web і CLI** | Повторювати власні правила перед публікацією | Локальний JSON preset: GPS/serial/unchecked як blocking criteria | Однакові рішення для тих самих fixtures; профіль нічого не завантажує |
| **Граф походження знахідки** | Пояснити вкладені витоки | Файл → вкладення → thumbnail → GPS; тільки структурні зв'язки | Кожне ребро веде до evidence, немає вигаданих зв'язків |
| **Локальний OCR як помічник** | Знаходити видимі email/телефони на сканах | Один image/PDF page, opt-in model, запропоновані рамки з ручним підтвердженням | Виміряні пропуски, false positives, час і RAM; OCR не стає гарантією очищення |
| **Пояснення суперечливих полів** | Побачити різні дати/GPS у EXIF/XMP/thumbnail | Показати конфлікт і джерела без висновку про підробку | Fixtures з відомими конфліктами й нормальними workflow |
| **Пакет до публікації** | Полегшити batch workflow | Copies + існуючий value-free receipt + короткий HTML summary без original values | Експорт не повертає приватні значення й не плутає unchecked з removed |
| **Лабораторія пошкоджень** | Навчальний диференціатор | Зміна CRC/довжини тільки synthetic sample, прогноз і фактичний parser result | Оригінал недоторканий, наслідки обмежені sandbox sample |

Пріоритет для продукту: план змін → зрозумілий copy result → семантичний compare. OCR починати як окремий вимірюваний експеримент; автоматичне редагування за його здогадками не вмикати.

## Рекомендована черга робіт

1. **Зафіксувати актуальну базу:** відокремити незавершені UI-зміни від новішого main, отримати baseline тести/runtime саме цільового commit. Не переносити всі 868 доданих рядків автоматично.
2. **Надійність:** admission budgets + parse deadline/reset + stronger fuzz assertions. Gate: bounded memory/time, відкриття наступного файла, жодного нового false Removed.
3. **Завершення copy workflow:** видимість skipped verification, план змін, єдиний result panel. Gate: людина розуміє, що створено і що фактично перевірено.
4. **Матриця пристроїв:** critical WebKit/Firefox suite та фізичні iOS/Android checks. Gate: download/share, PDF areas, keyboard/screen reader, low-memory recovery.
5. **Один продуктовий експеримент:** semantic compare або presets. Оцінювати час виконання задачі, помилки вибору та розуміння unchecked; не встановлювати телеметрію файлів.

## Виконана перевірка

- `pnpm --filter web test`: **48 файлів, 493 тести пройшли**.
- `cargo test --workspace --locked`: **exit 0**. У core unit suite 475 тестів; це не загальна кількість workspace tests. Шість `big` timing tests штатно ignored у debug.
- `pnpm --filter web build`: **exit 0**, TypeScript і Vite. Є попередження про classic `theme.js` scripts. WASM не перебудовувався: браузер використав наявні generated artifacts; source↔artifact parity цим не доведена.
- Headless installed Chrome через Python Playwright: головна, `photo.jpg`, `report.pdf`, viewport **1440×1000** і **390×844**, українська мова. У шести станах не було `pageerror` чи document-level horizontal overflow. Візуально переглянуто desktop photo й mobile PDF screenshots.
- Screenshots: `/private/tmp/hexscope-audit-{desktop,phone}-{home,photo.jpg,report.pdf}.png`. Це тимчасові артефакти.
- Не запускались у цьому проході: повний E2E suite, новий fuzz campaign, release performance benchmarks, незалежні readers, advisory database scan, physical devices, production/CI. Новіші `origin/main` і 0.18 runtime не запускалися.

Попередню знахідку про inbox без TTL не повторюю: поточний `public/sw.js` уже має `SHARE_TTL = 24h` та purge. Не пропоную вдруге реалізувати photo inspector, PDF navigation, WAV, ICC чи додаткові ZIP methods: вони присутні в новішій локально відомій історії.
