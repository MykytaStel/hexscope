## 1. Що це

**hexscope** — браузерний інструмент, який показує будь-який файл зсередини: структуру, байти й роботу алгоритму стиснення. Кидаєш файл у вкладку — бачиш дерево полів, підсвічені байти й покрокову анімацію розпакування. Нічого не вивантажується на сервер.

Одне речення для README: *A microscope for binary files — drop one in and watch it take itself apart, entirely in your browser.*

## 2. Проблема і користувачі

Щоб подивитись, що всередині файлу, сьогодні треба або читати специфікацію з `xxd` у другому вікні, або ставити десктопну програму. Браузерного інструмента, яким приємно користуватись, немає.

П'ять цільових сценаріїв, у порядку важливості:

1. **Зламаний файл.** «Сервер повернув побитий PDF», «чому цей ZIP не розпаковується». Людині треба знати, де саме ламається.
2. **Розробка парсера.** Пишеш імпорт формату — постійно звіряєш, де в байтах те поле, яке читаєш.
3. **Навчання.** Побачити структуру руками замість читання статті.
4. **Реверс / CTF / безпека.** Глянути на підозрілий файл, не запускаючи його. Локальність — вимога, не маркетинг.
5. **Приватність фотографій.** Людина кидає своє фото і бачить у EXIF GPS-координати. Це головний гачок для поширення.

Конкуренти: Kaitai Web IDE (потужний, але інженерний і незручний), ImHex (десктоп, важкий), 010 Editor (платний десктоп). Ніша «красиво, миттєво, у браузері, з поясненням» вільна.

## 3. Обсяг

### v1 — тільки PNG

PNG обрано першим, бо поєднує просту структуру (чанки + довжина + тип + CRC) з нетривіальним алгоритмом всередині (DEFLATE: LZ77 + Huffman + фільтри рядків), і тому що результат можна показати очима — розпаковані пікселі поруч із байтами. CRC дає безкоштовну діагностику пошкоджень.

**У v1 входить:**

- Парсер PNG: сигнатура, усі критичні чанки (IHDR, PLTE, IDAT, IEND) і поширені допоміжні (tEXt, pHYs, gAMA, tRNS)
- Перевірка CRC кожного чанка
- Повна реалізація inflate з покроковим трейсом
- Розпакування в пікселі + прев'ю зображення
- Інтерфейс за розкладкою B (секція 6)
- Анімація DEFLATE (секція 7)
- Робота зі зламаними файлами (секція 8)

**Поза v1:**

- Інші формати
- Редагування файлів (інструмент лише для читання — назавжди)
- Збереження/шеринг сесій, акаунти, бекенд будь-якого виду
- Мобільна розкладка. Інтерфейс розрахований на ширину від 1024px; на вужчих екранах сторінка не ламається, але окремої розкладки немає

### Роадмеп після v1

| Версія | Що | Чому в цьому порядку |
|---|---|---|
| v1.1 | **EXIF** з JPEG (APP1/TIFF), без декодування самого JPEG | Головний віральний гачок коштує 2–3 вечори замість місяця |
| v2 | **ZIP** | Один парсер відкриває .docx, .apk, .jar, .epub; рекурсія «зайти всередину» — сильна фіча |
| v3 | **WASM** | Найлегший парсер, аудиторія розробників, самореференційне демо |
| v4 | **Повний JPEG** (DCT + Huffman) | Найдорожчий, робимо коли решта стабільна |

Пізніше, окремим режимом: **«стаття»** — той самий розбір, поданий як вертикальна сторінка з поясненнями (варіант C із обговорення розкладок). Та сама модель даних, інший рендерер. Саме цей режим приноситиме людей із соцмереж.

## 4. Архітектура

Три шари. Кожен тестується окремо, межі між ними — явні.

### Шар 1 — Rust-ядро (`crates/hexscope-core`)

Кожен формат реалізує один трейт:

```rust
pub trait Format {
    /// Чи схожий початок файлу на цей формат.
    fn sniff(head: &[u8]) -> bool;
    /// Розібрати. Ніколи не панікує, завжди повертає дерево.
    fn parse(r: &mut Reader) -> ParseTree;
}
```

Вихід не залежить від формату — завжди дерево вузлів:

```rust
pub struct Node {
    pub id: NodeId,
    pub label: String,        // "IHDR", "width"
    pub range: ByteRange,     // зміщення + довжина у вихідному файлі
    pub value: Option<Value>, // декодоване значення, якщо є
    pub kind: NodeKind,       // Container | Field | Warning | Error
    pub children: Vec<NodeId>,
}
```

Фронтенд не знає, який це формат. Він рендерить дерево. Додати формат = додати крейт-модуль, фронтенд не чіпаємо.

### Шар 2 — межа WASM

Тут живе плавність. Три обов'язкові рішення:

1. **Парсинг у Web Worker.** Файл на 200 МБ на головному потоці — заморожена вкладка.
2. **Нуль копіювань.** Байти лежать у лінійній пам'яті WASM один раз. JS читає через `Uint8Array`-в'ю на ту саму пам'ять, ніяких `slice()`.
3. **Дерево перетинає межу один раз, плоскими типізованими масивами.** Не JSON: 100 тисяч вузлів як об'єкти — це секунди серіалізації. Структура-з-масивів + `postMessage` з `transfer`.

### Шар 3 — фронтенд (`apps/web`)

- **Абстракція рендерера.** Інтерфейс `Renderer.draw(viewport, highlights)`. Реалізація Canvas2D у v1; WebGPU — окремий бекенд пізніше, без змін у решті коду.
- **Віртуалізація.** Малюються лише видимі рядки. Розмір файлу не впливає на fps.
- **Індекс інтервалів.** Пошук вузла під байтом — O(log n) (відсортований масив діапазонів + бінарний пошук). Наївний обхід дерева на кожен `mousemove` — це і є типова «неплавність».

### Потік даних

```
drop → Worker → WASM parse → плоске дерево (transfer)
     → головний потік будує індекс інтервалів
     → рендерер малює видиме вікно
     → hover → бінарний пошук → підсвітка
```

Головний потік ніколи не парсить і не тримає власної копії байтів.

## 5. Технологічні рішення

| Рішення | Вибір | Чому |
|---|---|---|
| Мова ядра | Rust | Парсери, фаззинг, WASM без рантайму |
| Міст | `wasm-bindgen` + `wasm-pack` | Стандарт, працює з воркерами |
| Фронтенд | TypeScript + Vite, **без UI-фреймворку** | UI — це дерево, канвас і шухляда. Реконсиляція фреймворку на гарячому шляху лише заважає |
| Рендер | Canvas 2D за абстракцією | Достатньо для 60fps з віртуалізацією; WebGPU пізніше без переписування |
| Репозиторій | pnpm-монорепо: `crates/` + `apps/web` | Як у zvist і goodgames — звична структура |

Оборотні рішення: UI-фреймворк (можна додати, якщо chrome розростеться), WebGPU-бекенд. Необоротні на практиці: модель даних `Node` і плоский формат передачі — їх варто продумати один раз добре.

## 6. Інтерфейс (розкладка B)

Три зони:

- **Ліва колонка, ~180px** — дерево структури. Колірні мітки типів, червоні позначки помилок.
- **Основна зона** — полотно з байтами на всю висоту. Головний елемент, отримує максимум місця.
- **Нижня шухляда** — деталі вибраного поля + анімація алгоритму. Ховається, коли не потрібна.

Чому не класичні три колонки: анімація DEFLATE за природою горизонтальна (вікно 32 КБ тягнеться вліво), їй потрібна широка смуга, а не вузька права панель. І байти — головне, їм потрібна висота.

Відомий компроміс: ліва колонка вузька, довгі імена доведеться обрізати з тултипом.

Взаємодія:

- Наведення на байт підсвічує вузол у дереві, і навпаки
- Клік фіксує вибір, шухляда показує деталі
- Кольори типів однакові в дереві й на полотні — це єдиний спосіб читати полотно швидко

## 7. Анімація DEFLATE

Фіча, якої немає в жодного конкурента, і причина, чому проєкт цікаво писати.

Inflate веде трейс: для кожного кроку — чи це літерал, чи match, і якщо match, то `(відстань, довжина)`. Трейс показується в шухляді:

- Стрічка вже розпакованих байтів
- Поточна позиція
- Для match — **стрілка назад до місця, звідки копіюються байти**, і підсвічені обидва фрагменти
- Лічильники: частка літералів і match, поточний коефіцієнт стиснення
- Керування: крок уперед/назад, відтворення зі змінною швидкістю

Саме стрілка перетворює LZ77 з абстракції на очевидну річ. Це і є те, що люди знімають на відео й репостять.

Трейс може бути величезним, тому він **не матеріалізується цілком**: зберігаються контрольні точки стану через кожні N кроків, а між ними декодування переграється. Інакше 12 тисяч кроків з'їдять пам'ять.

## 8. Обробка помилок

**Правило: будь-який вхід повертає дерево.** Екрана «не вдалося розпарсити» не існує. Користувач найчастіше приходить саме зі зламаним файлом.

| Рівень | Приклад | Поведінка парсера |
|---|---|---|
| `Warning` | CRC не зійшовся, невідомий чанк | Жовтий вузол, дерево повне |
| `Recoverable` | Поле не читається, довжина за межами файлу | Червоний вузол із діапазоном, стрибок до наступного чанка |
| `Fatal` | Сигнатура не впізнана | Сирий hex + «формат невідомий»; байти все одно можна дивитись |

Реалізація: усі читання йдуть через `Reader`, який повертає `Result` і ніколи не індексує зріз напряму. `catch_unwind` на межі WASM — страхувальна сітка, а не стратегія.

## 9. Бюджети продуктивності

Це не побажання, а тести (секція 10, пункти 4–5).

| Дія | Бюджет |
|---|---|
| Наведення → підсвітка | < 16 мс |
| Парсинг PNG 10 МБ | < 300 мс |
| Скрол на файлі будь-якого розміру | 60 fps |
| Від drop до першого кадру | < 1 с |

**Про розмір файлу.** Штучної стелі не ставимо: віртуалізація робить fps незалежним від розміру, а реальна межа — це пам'ять браузера. Коли виділення пам'яті падає, показуємо зрозуміле повідомлення з фактичним розміром файлу, а не порожній екран.

## 10. Тестування

Усе в CI з першого тижня, не «колись потім».

1. **Golden-снапшоти** — корпус реальних PNG → знімок дерева через `insta`. Ловить регресії парсера.
2. **Фаззинг** — `cargo-fuzz` на вході парсера. Критерій: нуль паніки, нуль зависань. Стартовий корпус — **PngSuite**, у ньому вже є навмисно пошкоджені файли.
3. **Property-тест** — `proptest`: для будь-якого масиву байтів `parse()` завершується і повертає дерево.
4. **Бюджети як тести** — `criterion` перевіряє таблицю секції 9; CI падає при виході за межі.
5. **Плавність як тест** — Playwright-трейс на скриптованому скролі: жоден кадр не довший за 16 мс. Без цього плавність тихо деградує від релізу до релізу.
6. **Коректність inflate** — розпаковане ядром звіряється з еталоном (`flate2`) на всьому корпусі. Власна реалізація потрібна заради трейсу, але правильність доводиться порівнянням.
